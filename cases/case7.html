Problem

The Problem Space

Road damage and hazards go largely unreported across Indian cities. Municipal complaint portals exist but are high-friction — they require logins, long forms, and often go unacknowledged.

For everyday commuters, there's no quick, mobile-first way to flag a pothole or waterlogging in seconds. And without aggregated reports, civic bodies have no real-time visibility into road quality on the ground.

Core Question How do we make road reporting so fast and low-friction that everyday commuters actually do it?

Solution

Three-Tab Product Architecture

01

Report Tab

The core flow — select a location (auto or manual), drag the score slider from Critical to Excellent, and tag specific problems. Designed to complete in under 30 seconds. One thumb, one screen, done.

02

Map Tab

A live geographic view of aggregated road quality scores across the city. Colour-coded by severity — gives users and potentially civic bodies a spatial understanding of where the worst roads are.

03

Explore Tab

Browse reports by area, road name, or problem category. Lets users see what's been flagged near them and reinforces the community nature of the product.

Feature Deep-Dive

Location Selection — Getting It Right

Location selection was the highest-friction point in the report flow. Getting it wrong means bad data. Getting it right means the entire platform's integrity.

The Design Decisions

  • Auto-detect first — browser geolocation on load, no extra tap required
  • Graceful permission fallback — if denied, show manual search immediately, not an error state
  • Single card pattern — one location displayed at a time, no duplicate or stacked cards
  • "Change" link always visible — user can correct location regardless of how it was set
  • Result filtering — search distinguishes roads from landmarks, hospitals, metro stations
UX Principle A dead-end permission denial is a dropped report. Every friction point costs data quality. Graceful fallbacks are product decisions, not edge cases.
Key Iteration The single-card location display replaced an earlier design that showed both auto-detected and search results simultaneously — causing user confusion about which was active.

Feature Deep-Dive

Scoring & Problem Tagging

Drag-to-Score Slider

  • Range: 0 (Critical) to 100 (Excellent)
  • Drag interaction — fast, tactile, mobile-optimised
  • Numeric score visible in real time as user drags
  • Default state designed to avoid ambiguous "already scored" feel

Problem Tagging

  • Tap-to-select specific issue categories
  • Categories: potholes, cracks, waterlogging, broken surface, missing markings
  • Multi-select — a road can have multiple active problems
  • Tags feed into aggregate problem frequency on the map
Design Intent Scoring a road shouldn't feel like filling a form. The drag slider gives instant tactile feedback — users feel like they're making a quick, confident judgement, not completing a survey.
Data Use Aggregated scores per road segment surface an average quality rating on the map, weighted by recency. Problem tag frequencies drive a severity heatmap overlay.

Technical

How It's Built

Frontend

  • React — component-driven, mobile-first layout
  • Browser Geolocation API for auto-location detection
  • Custom drag-to-score slider component
  • Tab-based navigation (Report / Map / Explore)

Infrastructure

  • Deployed on Vercel — zero-config, instant deploys
  • Mobile-first responsive design, no native app required
  • Lightweight — loads fast on 4G mobile connections
Why React + Vercel? Fast iteration cycle. As a PM building solo, the stack needed to get from idea to live prototype in days, not weeks. React's component model lets me isolate and fix UX issues (like the location card) without touching the rest of the flow.
PM Insight Building this myself gave me direct empathy with the engineering side — every UX decision I made had to be feasible to implement alone in a weekend. That constraint made the design better, not worse.

Learnings

What Building This Taught Me

L1

Fallbacks Are First-Class Features

The geolocation permission-denied state was an afterthought in v1 — it broke the entire report flow for users who denied access. Treating edge cases as primary user journeys is a product discipline, not a QA task.

L2

Search Disambiguation Is Harder Than It Looks

Distinguishing "Sector 20 Road" from "Sector 20 Metro Station" in search results requires deliberate result filtering. Generic place APIs return hospitals, schools, and landmarks — not roads. This is a data quality problem, not just a UX one.

L3

Default States Carry Product Intent

The score slider's default position (mid-range vs no default) significantly changes user behaviour. An ambiguous default makes users second-guess themselves. Opinionated defaults are a product decision — not just a UI detail.
